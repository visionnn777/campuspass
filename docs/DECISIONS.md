| 10 | 2026-10-26 | §2 sessions | `get_current_user` commits its implicit read transaction. Services then open `with db.begin():`. | SQLAlchemy can't `begin()` while an implicit transaction is open. `expire_on_commit=False` keeps the user object usable. |
| 11 | 2026-10-26 | §8 | Every lock query uses `execution_options(populate_existing=True)`. | Otherwise SQLAlchemy could return a stale copy of the row already in the session instead of the freshly locked values. |
| 12 | 2026-10-26 | §7 capacity | On a capacity change, promotion uses `new_capacity − occupancy` (can promote several people). Cancellation promotes at most one, as specified. | That's exactly the number of free seats. |
| 13 | 2026-10-26 | §10 | Self-cancel on a **cancelled event** is allowed (recorded, no promotion). | It's harmless, and it lets students clean up their list. Promotion already checks `status = published`. |
| 14 | 2026-10-26 | §6 body limit | Requests with neither `Content-Length` nor chunked encoding are treated as having an empty body. Chunked without a length gives 411. | This matches HTTP/1.1 semantics. Bodiless POSTs like `/publish` must keep working. |
| 15 | 2026-10-26 | §5 admin | Every admin user update locks the actor, target, and active-admin rows **together ordered by UUID**. | A consistent lock order for user rows prevents a deadlock when two admins disable each other, and enables the last-admin count (test 14). |
| 16 | 2026-10-26 | §12 codes | Added codes for cases the spec described only generally: `NOT_AUTHENTICATED`, `INVALID_TOKEN`, `INVALID_CREDENTIALS`, `FORBIDDEN`, `VALIDATION_ERROR`, `EVENT_NOT_FOUND`, `REGISTRATION_NOT_FOUND`, `USER_NOT_FOUND`, `NOT_FOUND`, `METHOD_NOT_ALLOWED`, `BAD_REQUEST`, `PAYLOAD_TOO_LARGE`, `LENGTH_REQUIRED`, `RATE_LIMITED`, `INTERNAL_ERROR`, `DATABASE_UNAVAILABLE`, `BUSY`. | One machine-readable code per distinct situation. |
